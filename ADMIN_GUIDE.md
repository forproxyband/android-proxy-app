# Proxy Agent — справка для системного администратора

Практическое руководство по работе с приложением: что показывает каждый
элемент главного экрана, как настроить подключение, как читать и сохранять
логи, как запустить ротацию IP и что делать, если ротация не отрабатывает.

---

## 0. Требования к устройству

| | Минимум | Рекомендуется |
| --- | --- | --- |
| **Android** | 6.0 (API 23) | 11+ (API 30) — добавит kernel `splice(2)` zero-copy на TCP fast path (~3× ниже CPU на нагрузке) |
| **Архитектура** | arm64-v8a | arm64-v8a — единственная поддерживаемая. armv7 / x86 устройства не запустятся (в APK нет соответствующих `.so`) |
| **SIM** | с активным мобильным интернетом | — |
| **Root** (Magisk / SuperSU) | не требуется для базовой работы агента | **обязателен для смены IP**. Без root ↻-ротация и серверный REBOOT-цикл отработают, но IP обычно не сменится — оператор удержит PDP-контекст (см. §4) |
| **`WRITE_SECURE_SETTINGS`** | — | частичная замена root: даёт airplane toggle во время ротации (IP всё равно не сменится без root) и one-tap fix `mobile_data_always_on=1` для Wi-Fi return preflight. Грантится один раз: `adb shell pm grant com.proxyagent.app android.permission.WRITE_SECURE_SETTINGS` |
| **Battery whitelist** | — | для долгих сессий — кнопка `ALLOW BACKGROUND` на главном экране |
| **OEM autostart** | — | на Xiaomi / Huawei / Samsung / OnePlus / Oppo / Vivo одна разовая настройка, иначе сервис не поднимется автоматически после обновления APK — см. §7.7 |

> **Почему минимум Android 6.0 (API 23):**
> - `ConnectivityManager.bindProcessToNetwork` — основа split-routing'а для Wi-Fi return; до API 23 не существует.
> - `NetworkCapabilities.NET_CAPABILITY_VALIDATED` — фильтр captive-portal Wi-Fi; без него релей мог бы тихо ехать в дохлую сеть.
> - `PowerManager.isIgnoringBatteryOptimizations` + диалог `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — без них Doze убивает длинные сессии.
>
> На Android 5.x приложение **не установится** (`minSdk=23` в манифесте — Play Store / `adb install` откажут).

## 1. Главный экран — что где

```
┌─────────────────────────────────────────────────────┐
│                    PROXY AGENT                      │   ← заголовок + версия
│              v2.0.x  build NNN                      │
│             1.2.3.4  ·  CELLULAR                    │   ← публичный IP + транспорт
│                                                     │
│                    CONNECTED                        │   ← статус-бейдж
│                ↓ 12 Mb/s  ↑ 3 Mb/s                  │
│                                                     │
│  ┌─ зелёная панель «виджет подключения» ─────────┐  │
│  │ CONNECTED TO REGISTRATOR                      │  │
│  │ 198.51.100.7:443        up 00:42:17           │  │
│  │ ⇅ 4 tunnels · QUIC                            │  │
│  │ ‹ swipe for 24h graphs ›                      │  │
│  └───────────────────────────────────────────────┘  │
│  ● ○ ○ ○   ← индикатор страниц (свайп влево/вправо) │
│                                                     │
│  [   START   ] [ ↻ ] [ ◫ ] [ ⚙ ]                    │
│                                                     │
│  Auto-stop below battery: [  Off  ▾]                │
│  [ ALLOW BACKGROUND (BATTERY WHITELIST) ]           │
│                                                     │
│  LOGS                              [SAVE]   ▼       │
│  ┌─────────────────────────────────────────────┐    │
│  │ 12:03:14 supervisor start                   │    │
│  │ 12:03:14 uplink dialing endpoint=…          │    │
│  │ 12:03:15 uplink connected transport=quic    │    │
│  │ …                                           │    │
│  └─────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘
```

### 1.1. Шапка
- **Версия приложения** (`v2.0.x build NNN`) — потребуется при сообщении о
  проблеме.
- **Сетевая строка** — текущий публичный (NAT) IP + тип транспорта Android
  (`CELLULAR` / `WIFI` / `ETHERNET` / `VPN` / `NONE`). Обновляется при смене
  сети и раз в 5 минут.

### 1.2. Статус-бейдж
Крупная цветная надпись под сетевой строкой. Приоритет (первое совпадение
выигрывает):

| Бейдж | Цвет | Значение |
| --- | --- | --- |
| `ROTATING · <stage>` | оранжевый | идёт авто-ротация IP, текст — текущий шаг |
| `STOPPING…` | оранжевый | вы нажали STOP, ждём остановки процесса |
| `NOT CONFIGURED · TAP START TO IMPORT` | оранжевый | подключение не настроено |
| `ERROR` | красный | агент аварийно остановился — смотрите логи |
| `AUTO-STOPPED · <reason>` | оранжевый | автостоп (батарея/нет интернета) |
| `CONNECTED  ↓ X ↑ Y` | зелёный | туннель работает, показаны скорости |
| `CONNECTING…` / `RECONNECTING…` / `STARTING…` | оранжевый | переходные состояния |
| `RUNNING` | зелёный | сервис запущен, но детального статуса ещё нет |
| `DISCONNECTED` | красный | агент не запущен |

### 1.3. Виджет подключения (зелёная панель)
Появляется, когда сервис работает. **Свайпом влево/вправо** переключаются
4 страницы (точки под панелью показывают активную):

| Стр. | Что показывает |
| --- | --- |
| ● — статус | хост:порт регистратора, аптайм, число активных туннелей, текущий транспорт (QUIC / TCP (splice) / TCP+yamux / WebSocket), мгновенные скорости ↓/↑ |
| ○ — TRAFFIC · LAST 24H | мини-график трафика за последние 24 часа + суммарный объём |
| ○ — CONNECTIONS · LAST 24H | мини-график числа подключений за 24 часа |
| ○ — ROTATIONS · LAST 24H | гистограмма ротаций IP за 24 часа (■ manual, ■ auto) |

### 1.4. Кнопки управления

| Кнопка | Назначение |
| --- | --- |
| `START` / `STOP` | запуск/остановка сервиса. Если подключение не настроено — откроется диалог с предложением сканировать QR или открыть настройки |
| `↻` | **ручная ротация IP** — останавливает агента, прокручивает сотовое соединение, поднимает снова. Видна только при работе через CELLULAR; на Wi-Fi появится Toast «Disable WiFi to cycle mobile IP» |
| `◫` | открыть экран **аналитики** (за день/неделю/месяц) |
| `⚙` | открыть **настройки** подключения |

### 1.5. Авто-стоп по батарее
Выпадающий список `Auto-stop below battery`: `Off`, `5%`, `10%`, `15%`,
`20%`, `30%`. Если выбран не-`Off` и уровень заряда падает до или ниже
порога — сервис останавливается с причиной `Battery N% ≤ T% — auto-stopped`.
Работает в том числе во время ротации.

### 1.6. Battery whitelist
Кнопка `ALLOW BACKGROUND (BATTERY WHITELIST)` появляется, **только если
приложение не в whitelist** Android Battery Optimization. Жмёте — открывается
системный диалог разрешения работы в фоне. Без этого Android может
прибивать `:proxy`-процесс при длинных сессиях.

> На Xiaomi / Huawei / Samsung / OnePlus / Oppo / Vivo этого
> **недостаточно** для автозапуска сервиса после обновления
> приложения. У этих OEM есть отдельные «защитники», которые
> блокируют broadcast'ы и автозапуск даже когда приложение в
> battery whitelist. Если устройство — одна из этих марок, см.
> §7.7 — там пошаговые инструкции по моделям.

## 2. Логи

### 2.1. Раскрыть/свернуть
Заголовок `LOGS` с шевроном `▼` — кликабельный. Состояние «раскрыт/свёрнут»
запоминается (`logs_expanded` в SharedPreferences). В раскрытом виде —
зелёный монохромный «терминал», автопрокрутка вниз по мере появления
строк. В свёрнутом — освобождает место под виджет.

### 2.2. Что там показывается
Это «хвост» stdout бундлд-бинаря (или NATIVE-движка), с временной меткой,
который пишется в `agent.log` в `filesDir`. Ротируется при превышении
30 MiB до 25 MiB. Ключевые строки, по которым можно ориентироваться:

- `supervisor start` — агент стартует.
- `uplink dialing endpoint=…` — пытается соединиться с регистратором.
- `uplink connected … transport=quic|tcp` — AUTH прошёл, туннель поднят.
- `opening tunnel` / `opening quic tunnel` — приходит новое подключение.
- `tunnel target dial failed` — целевой ресурс не отдался, обычно сетевая
  проблема со стороны цели или DNS.
- `REBOOT received from registrator` — сервер попросил сменить IP, дальше
  включается авто-ротация.
- `reconnect backoff` — экспоненциальный откат при разрыве (250 мс → 10 с).
- `uplink AUTH denied (control closed before reply)` — ключ/UUID не приняты
  сервером, проверить настройки.

### 2.3. Сохранить логи (кнопка `SAVE`)
Жмёте `SAVE` в шапке `LOGS` → формируется файл
`proxy-agent-<YYYYMMDD-HHMMSS>.log` с шапкой device-info (статус
подключения, регистратор, текущая скорость, версия приложения и т.д.) и
телом из `agent.log`. Открывается системный chooser
«Save / share log» — можно отправить в мессенджер, почту, сохранить в
Downloads и т.п.

Если жмёте до того, как был хоть один запуск агента → Toast
«No log to save yet».

> **Где хранится локально**: `filesDir/exports/proxy-agent-*.log`.
> Старые snapshot-файлы стираются при следующем `SAVE`, чтобы не копились.

## 3. Настройки (`⚙`)

Диалог открывается кнопкой `⚙`. Поля:

### 3.1. Connection mode
- **Modem tunnel (direct registrator)** — **режим по умолчанию.** Прямой
  коннект к регистратору по `host:port` с заданным `Agent Key` и
  опциональным `Agent ID`. Это основной режим для модемов/SIM-боксов,
  именно под него рассчитаны QR-коды агентов. После чистой установки
  и после сканирования QR режим всегда стоит в Modem — менять вручную
  не требуется.
- **Residential (via balancer)** — узкоспециализированный режим: клиент
  сам ходит на балансировщик и получает оттуда адрес регистратора.
  Используется только для residential-стека; переключайте сюда, **только
  если так сказал менеджер**.

При импорте по QR режим **принудительно ставится в Modem**, даже если
до этого был выбран Residential.

### 3.2. Share connection — SCAN QR / IMPORT / EXPORT
Эти три кнопки экспортируют/импортируют **только поля подключения**:
`mode`, `host`, `port`, `key`, `id`, `dns`. Локальные настройки
(автостоп, единицы скорости, retention) **не передаются** — они per-device.

- **SCAN QR — основной способ настройки.** Видна в режиме Modem.
  Доступны три источника, которые открываются через chooser:
  1. **Live camera** — навести камеру на QR-код, выданный по агенту
     (ML Kit barcode scanner).
  2. **Image from gallery** — выбрать PNG/JPG со скриншотом QR-кода
     (ZXing).
  3. **Paste from clipboard** — вставить plain-text содержимое QR из
     буфера обмена (полезно, когда QR пришёл в чат текстом).

  После успешного сканирования поля `host` / `port` / `key` / `id` /
  `dns` заполняются автоматически, режим принудительно ставится в
  **Modem**, показывается Toast «QR applied: host, port, key, …».
  Дальше — `Save` → `START`.

  Содержимое QR — текстовые `key=value`-строки в том же формате, что
  и у EXPORT.

- **IMPORT** — резервный способ, когда нет QR. Открывает системный
  file picker, читает текстовый файл с теми же `key=value`-строками
  (комментарии `#` игнорируются, разделитель `=`), применяет только
  разрешённые ключи.
- **EXPORT** — для передачи конфигурации между устройствами.
  Формирует текстовый файл вида
  ```
  # Proxy Agent — Connection Settings Export
  # Generated: 20260525-103214
  mode=modem
  host=…
  port=…
  key=…
  id=…
  dns=…
  ```
  и открывает chooser для шаринга (мессенджер, почта, сохранение в
  Downloads). Файл потом импортируется на другом устройстве через
  `IMPORT` либо вставляется в режиме «Paste from clipboard» в QR.

### 3.3. Поля подключения
После сканирования QR эти поля заполняются автоматически — править
вручную нужно только в исключительных случаях (например, переопределить
DNS под конкретное окружение).

- **Host / Port** — адрес регистратора (modem) или балансировщика
  (residential).
- **Agent Key** — ключ авторизации, обязательное поле.
- **Agent ID** (modem UUID) — идентификатор агента, по умолчанию равен
  ключу. Часто формат `KEY_PORT`.
- **DNS servers** — список через запятую (пусто = `1.1.1.1,8.8.8.8`).

### 3.4. Show speed in MB/s (bytes)
Переключает индикацию скорости и графики между **битами** (`Mb/s`,
по умолчанию) и **байтами** (`MB/s`).

### 3.5. Analytics retention
Сколько дней хранить аналитические бакеты (трафик/подключения/ротации).
Дефолт — 30 дней. Старее — удаляется при запуске приложения.
Объём — примерно 1 MB за активный день.

### 3.6. Engine
- **Native Kotlin (recommended)** — производственный путь и
  дефолт для новых установок. Встроенный pure-Kotlin порт SDK,
  работает в том же `:proxy`-процессе. Поддерживает Wi-Fi return,
  кернельный `splice(2)` zero-copy и in-house QUIC v1 стек с
  Brutal congestion control (kwik-адаптер остался скомпилирован
  как safety-net, но не выставлен в UI).
- **Binary subprocess** — запускает встроенный ELF-бинарь
  `libproxyagent.so` через `ProcessBuilder`. Legacy /
  диагностический вариант, **временно** оставлен для сравнения и
  будет удалён, когда NATIVE наберёт достаточно полевых часов.
  Wi-Fi return через него **не работает корректно** (см. §3.9);
  смена движка требует STOP → START.

> Старый AAR-движок был полностью удалён из приложения 2026-05-28 —
> он никогда не выходил end-to-end в этой сборке SDK (Modem-режим
> не доходил до AUTH), и 25 MiB gomobile-артефакта впустую раздували
> APK. Если у вас в логах или прошивке упоминается AAR — это
> устаревший след, игнорируйте.

### 3.7. Network optimization

Выпадающий список под `Engine`. Подстраивает сетевой стек агента
под ожидаемый потолок канала — три пресета, **дефолт `LOW_100`**:

- **100 Mbps — low latency (cellular / Wi-Fi)** — для сотовой связи
  и обычного Wi-Fi. Маленькие буферы и агрессивная отдача
  flow-control credit → задержки и плавность не страдают, даже
  когда канал реально загружается под потолок.
- **500 Mbps — balanced** — для крепкого Wi-Fi 5/6 или мощной
  магистрали. Средние буферы, средняя частота refresh.
- **1 Gbps — max throughput** — для симметричного гигабита
  (Ethernet через USB-C, Wi-Fi 6E с хорошим линком). Толстые
  буферы, чтобы не упираться в потолок при заливке, ценой того,
  что задержки могут «плыть».

**Что крутится пресетом** (под капотом — для тех кто читает логи):

| Пресет | Brutal CC | UDP буфер QUIC | Refresh окна FC | TCP SO_*BUF | TCP bridge буфер |
| --- | --- | --- | --- | --- | --- |
| 100 | 100 Мбит/с | 4 MiB | 25% consumed | 1.5 MiB | 64 KiB |
| 500 | 500 Мбит/с | 16 MiB | 40% consumed | 6 MiB | 128 KiB |
| 1000 | 1 Гбит/с | 32 MiB | 50% consumed | 12 MiB | 256 KiB |

QUIC-окна flow-control (`initialMaxData=160 MiB`,
`initialMaxStreamData=16 MiB`) **остаются неизменными во всех
пресетах** — production-validated значения, занижение ломало
uploads через прокси-сервер (build-93 incident).

**Когда применяется.** При нажатии `Save` значение пишется в
SharedPreferences, но к **уже работающему туннелю не применяется
на лету** — параметры QUIC ездят в TLS-хендшейке, не
перерубаются на ходу. Тост говорит `Saved — restart agent to
apply`: остановите и снова стартуйте сервис (`STOP` → `START`),
и новый туннель поднимется с новыми параметрами.

**Какой пресет выбрать.** В сомнении ставьте `LOW_100` —
большинство мобильных линков ниже 100 Мбит/с реально, и при
лишнем запасе bufferbloat создаёт «лагающие» задержки даже на
норм канале. На быстром Wi-Fi 6 / Ethernet можно ставить выше.
Эмпирический критерий: запустите speedtest через прокси, если
канал реально упирается в текущий пресет и не больше — повысьте.
Если же speedtest показывает например 200 Мбит/с на пресете
`HIGH_1000`, а ping/latency «плавают» — понизьте до `MID_500`.

**Только NATIVE-движок.** Бинарь
(`libproxyagent.so`) не знает про пресет — у его QUIC-стека Brutal
CC и UDP-буфер вкомпилены константами (см.
[BINARIES.md](BINARIES.md) §2). При выборе `Binary subprocess`
спиннер пресета **серый, hint притемнённый** — выбор сохранится,
но не применится. При запуске бинаря с не-дефолтным пресетом в
логах появляется строка:

```
WARN: network_profile=MID_500 ignored — binary engine uses fixed
100 Mbps Brutal CC / 32 MiB UDP buf. Switch to NATIVE engine to
honor this setting.
```

**Проверка применения** в `agent.log` (раздел §2.3 — кнопка
`SAVE` логов). При успешном старте NATIVE-движок печатает одну
структурированную строку:

```
level=INFO msg="network profile" user_choice=LOW_100
  tcp_socket_buf=1500000 tcp_bridge_buf=65536
  quic_brutal_target_mbps=100 quic_udp_socket_buf=4194304
  quic_window_headroom_ratio=0.75
```

`user_choice` показывает что выставил пользователь, остальные
поля — что реально применилось. Расхождение между ними возможно
только если SharedPreferences и intent extra рассинхронизированы
(не должно быть, но удобно проверить).

### 3.8. IP rotation fallbacks (требуется root)
> Root нужен для **любой** ротации (см. §4). Эти галки — дополнительные
> агрессивные методы поверх базового цикла, нужны **только если базовая
> 2-шаговая «ядерная» ротация у вашего оператора не меняет IP**. Если
> меняет — оставьте обе выключенными, тогда базовый цикл отработает
> быстрее.

- **APN swap** — переключает preferred APN на альтернативный (или
  дублирует текущий с пометкой `ProxyAgent-rotation-tmp`), делает airplane-
  cycle, возвращает обратно. Срабатывает только если на SIM прописано
  ≥ 2 APN под текущим `numeric` (MCC+MNC). **Требует root.**
- **IMEI rotation** — вызывает команду смены идентификатора и
  переподнимает радио.

  > ⚠️ **Функция не протестирована командой.** Алгоритм заложен в код,
  > но в реальных условиях на разных чипсетах/прошивках мы её не
  > прогоняли. Включайте на свой риск и обязательно сверяйте результат
  > с реальным IMEI (`AT+CGSN` на модеме, не Android API) — иначе
  > рискуете «менять» IMEI только для Android, а оператор будет видеть
  > старый.

  Требования:
  - **root** (Magisk / SuperSU);
  - **специальный Magisk-модуль**, который собственно меняет IMEI —
    приложение само по себе IMEI **не меняет**, оно только дёргает
    стороннюю команду через `su -c`.

  Метод выбирается ниже:
  - `custom` — выполнить произвольную команду из поля
    `Custom root command` через `su -c`. Например, `magisk-imei --random`
    или собственный скрипт. Что именно подставить — зависит от того,
    какой модуль вы поставили.
  - `props` — `resetprop -n -p ro.ril.imei0 <random15digits>`. Требует
    модуль **MagiskHidePropsConfig**. **Это spoof только на Android-
    уровне**: значения подменяются в системных property, но модем по-
    прежнему сообщает оператору настоящий IMEI. На практике для
    операторов, привязывающих IP к IMEI, **бесполезно**.
  - `magisk-imei` — `magisk-imei --random`. Требует одноимённый модуль
    `magisk-imei` (должен лежать в `PATH` у `su`).

  Эффективность сильно зависит от чипсета (Qualcomm / MediaTek /
  Exynos ведут себя по-разному) и того, что именно умеет конкретный
  Magisk-модуль на конкретной прошивке. Если ничего из этого не
  установлено — галку включать бесполезно: команда не найдётся, в
  логах будет `su: ... not found` или подобное.

> Включение **любой** из этих галок пропускает базовый 2-шаговый цикл
> и сразу идёт в выбранный fallback — общий бюджет ротации растёт на
> ~50 секунд на каждую активную галку.

### 3.9. Uplink routing — Return traffic to client over Wi-Fi

Опциональная экономия мобильного трафика. Когда галка включена и
устройство держит валидный Wi-Fi, **связка агент↔регистратор** (всё
содержимое клиентских запросов и ответов) идёт по Wi-Fi, а **исходящий
коннект агент→цель** по-прежнему уходит через сотовую — то есть
конечный сайт всё так же видит мобильный IP, как и без галки. На
типичном профиле это экономит примерно половину мобильного трафика
(всё, что прокачивается в обе стороны между телефоном и сервером).

**Поведение при отвале Wi-Fi:** связь не рвётся. Релей продолжает
принимать локальные подключения и направлять их через дефолтную сеть
(сотовая). Как только Wi-Fi возвращается, новые подключения снова идут
через него — без перезапуска агента. Существующие открытые сокеты
остаются на той сети, к которой были привязаны при старте; это
ограничение TCP, не приложения.

**Ограничения:**
- Доступно **только в Modem-режиме.** В Residential/Balancer режиме
  чекбокс задизейблен с подписью `(Modem mode only)` — балансировщик
  возвращает SDK адрес реального регистратора, мимо нашего локального
  релея, поэтому относительно балансера фича не работает (запланирована
  на следующую итерацию).
- **Требует NATIVE engine.** Когда галка ставится, приложение
  автоматически переключает `Engine` на `Native Kotlin` и отключает
  выбор `Binary subprocess`. Причина техническая: split-routing target
  dials через cellular требует `bindProcessToNetwork`, который
  работает только для текущего процесса — BINARY-субпроцесс не
  унаследует этот bind и target dials уйдут через Wi-Fi (то есть
  target увидел бы Wi-Fi IP вместо мобильного, что ломает всю
  ценность). На save показывается Toast `Wi-Fi return requires the
  NATIVE engine — switched automatically`.
- Используется только проверенная (`VALIDATED`) Wi-Fi сеть. Captive-
  portal Wi-Fi (отель/кафе, где нужно «принять условия» в браузере) не
  подхватится — пока не пройдёт валидацию, релей идёт через сотовую.
- Без `root` работает. Это не VPN, не системный сплит — просто
  локальный TCP-релей.
- Учёт трафика (`↓ ↑` в карточке статуса) показывает сумму по обоим
  интерфейсам, не разделяя Wi-Fi и сотовую. Это технически возможно
  починить, но не сделано — для оценки экономии смотрите системную
  «Использование данных» по приложению `Proxy Agent`.

**Когда включать:** на стационарных установках, где есть постоянный
Wi-Fi (склады, офисы, фермы модемов с роутером рядом). На мобильных
устройствах с непостоянным Wi-Fi включать тоже можно — отвал Wi-Fi
безопасен, просто экономия пропадёт.

**Индикатор в виджете подключения.** На первой странице виджета (где
имя регистратора, аптайм и активность) появляется блок из двух строк:

- **Голубым** — `↺ uplink: Wi-Fi · 433 Mbps · 5 GHz · Wi-Fi 5`
  (скорость / диапазон / стандарт берутся с реального линка). Под ним:
  ```
    ↓ exit:   203.0.113.10 (cellular)
    ↑ uplink: 198.51.100.20 (Wi-Fi)
  ```
  **Это и есть 100%-ное подтверждение.** Два разных публичных IP =
  трафик действительно разделяется. Exit IP (cellular) — это то, что
  видит целевой сайт; uplink IP (Wi-Fi) — то, что видит регистратор.
- **Жёлтым** — `↺ uplink via cellular · Wi-Fi return enabled but no
  Wi-Fi held`. Релей включён, но Wi-Fi сейчас недоступен/не
  валидирован, аплинк идёт через сотовую. Экономии нет, агент работает.
- **Жёлтым с предупреждением** — `⚠ uplink: Wi-Fi (target dials leak
  Wi-Fi IP)`, ниже два IP + строка `⚠ BINARY engine — target sees
  Wi-Fi IP, not cellular`. Это происходит на **BINARY engine** + Wi-Fi
  return: subprocess не наследует процессный bind на cellular,
  поэтому исходящие к таргетам уходят через Wi-Fi (default route).
  Uplink-savings работают (трафик к регистратору экономится), но
  таргет видит Wi-Fi IP вместо мобильного. Это **известное
  ограничение архитектуры BINARY** — для настоящего split-routing'а
  с in-process управлением сокетами используйте **NATIVE engine**
  (он же дефолтный).

- **Красным** — `✗ Wi-Fi return DISABLED · split routing not
  confirmed`, ниже:
  ```
    ↓ exit:   1.2.3.4 (cellular)
    ↑ uplink: 1.2.3.4 (Wi-Fi)
    ⚠ both IPs equal — OS suppresses cellular while Wi-Fi up
  ```
  Self-test обнаружил один из двух сценариев:
  1. **`SAME_IP`** — устройство **не разделяет** трафик, оба интерфейса
     дают одинаковый публичный IP (сотовая глушится при Wi-Fi). Решение:
     включить `mobile_data_always_on` (см. §3.9) и перезапустить сервис.
  2. **`LEAK_DETECTED`** — split физически работает, но **дефолтный
     роут** идёт через Wi-Fi (а не cellular как должно), то есть SDK
     target dials уходят через Wi-Fi и target видит Wi-Fi IP, а не
     мобильный. Это бывает на BINARY engine (его субпроцесс не
     наследует процессный bind на cellular), или если cellular
     недоступен в момент старта. Если используется BINARY engine —
     переключитесь на NATIVE (приложение должно было сделать это
     автоматически при ставке галки). Если NATIVE и всё равно LEAK —
     проверьте что SIM активна и cellular приходит при отключенном
     Wi-Fi.

  В обоих случаях **релей автоматически отключился**, агент работает
  через сотовую напрямую.
- Если ничего нет — релей выключен в настройках.

**Self-test двух публичных IP запускается автоматически:**
- через 5 секунд после старта сервиса (даём Wi-Fi network время
  присоединиться);
- при каждой смене Wi-Fi сети (новый SSID, переподключение) — с
  3-секундной задержкой и debounce 2 секунды на случай повторных
  `onAvailable` при handover;
- **один раз** через 5 секунд после каждой REBOOT auto-ротации IP —
  чтобы обновить cached cellular IP в виджете.

Что НЕ запускает лишних тестов:
- Во время ротации (`ROTATING · …` в бейдже) — все retest'ы по
  смене Wi-Fi подавляются. Иначе при каждой ротации мы бы жгли
  мобильный трафик на ipify-probe, а split-routing свойство и так
  не меняется при ротации — меняется только значение мобильного
  IP.
- Манульная `↻` ротация — стопает и стартует сервис целиком, тест
  пройдёт штатно при следующем старте.

Результат теста кешируется в `wifi_info.json` и подхватывается виджетом
без задержки.

В сохранённый лог (кнопка `LOGS → SAVE`) попадает:
- В секции `[CONNECTION STATE]` строка `Wi-Fi-Return: <state>`.
- Новая секция `[WI-FI RETURN]` с подробностями: `Cellular-Public-IP`,
  `Wi-Fi-Public-IP`, `Wi-Fi-Link-Speed` (Mbps), `Wi-Fi-Frequency` (MHz),
  `Wi-Fi-Band`, `Wi-Fi-Standard`, `Split-Routing` (VERIFIED / FAILED /
  PARTIAL / INCONCLUSIVE), `Self-Test-At`, `Self-Test-Detail`.
- Там же session-байт-счётчики (если был трафик): `Wi-Fi-Session-Tx`,
  `Wi-Fi-Session-Rx`, `Wi-Fi-Session-Saved` (= Wi-Fi-Tx+Rx, то что не
  ушло по мобильному), `Cellular-Target-Tx`, `Cellular-Target-Rx`
  (что отправил/получил агент target'ам через сотовую), и
  `Cellular-Fallback-Tx/Rx` если релей в какой-то момент был в
  fallback. Считают полную сессию (от старта сервиса до stop'a) — для
  понимания фактической экономии «N MB» отправь лог с включённым
  Wi-Fi return после 10 минут работы.

**На виджете** под двумя IP появляется ещё одна строка живых
счётчиков, например: `Session: Wi-Fi ↑12.4M ↓48.1M · target ↑8.2M ↓2.1M
· saved 60.5M`. Обновляется каждую секунду. Если релей был в fallback —
в строке появится дополнительный блок `Cell-fb ↑X ↓Y`. Если релей
выключился из-за split_failed — строка краснеет и блок `saved`
скрывается (нечего сохранять).

**Аналитика (`◫` экран)** работает в двух режимах в зависимости от
того, включён ли Wi-Fi return:

- **Wi-Fi return ВЫКЛЮЧЕН** (галка снята) — бакеты пишутся как раньше:
  `rx/tx` через `TrafficStats` (общий трафик приложения по UID),
  плюс `reg/nat/tr/op/cl/pk`. Поля `wrx/wtx/crx/ctx` остаются нулями
  — без релея у нас нет точной информации о разделении по интерфейсам,
  и приложение принципиально не пытается её угадать. Графики
  трафика и подключений работают как обычно.

- **Wi-Fi return ВКЛЮЧЁН и релей запущен** — дополнительно пишутся
  `wrx/wtx` (трафик через Wi-Fi когда релей реально был на Wi-Fi) и
  `crx/ctx` (трафик через сотовую — target dials + relay fallback).
  CSV-экспорт получает эти колонки, и сумма `wrx+wtx` за период даёт
  точную цифру «сколько мобильного трафика сэкономлено».

В обоих режимах:
- Старые бакеты (созданные до выхода wifi_return) читаются без
  поломки — у них эти поля просто 0.
- Поле `transport` (`tr`) в бакете показывает **дефолтный интерфейс**
  Android в момент tick. При активном split-routing'е через cellular
  process bind оно может писать `CELLULAR` даже когда часть трафика
  идёт по Wi-Fi через релей. Это не баг отчёта — используйте `wrx/wtx`
  vs `crx/ctx` для точного разделения, а не поле `tr`.

**Проверка «может ли устройство держать оба интерфейса».** При установке
галки приложение запускает фоновую проверку (≤5 с): читает системную
настройку `mobile_data_always_on`, если та `0` — пробует активный probe
через `requestNetwork(TRANSPORT_CELLULAR)`. Если устройство отрубает
сотовую при подключении к Wi-Fi — появляется диалог `Cellular may drop
while on Wi-Fi`. Возможны два сценария:

1. **Приложению выдана `WRITE_SECURE_SETTINGS`** (одна команда `adb`,
   та же что нужна для ротации IP без рута). В диалоге появляется
   кнопка `Enable` — приложение само пишет
   `mobile_data_always_on=1` и проверяет, что значение прижилось.
2. **Не выдана.** Диалог предлагает кнопку `Show instructions` — она
   открывает второй диалог с тремя путями:
   - **A**: `Settings → System → Developer options → Mobile data
     always active` (developer options сами включаются 7 тапами по
     `Build number` в `About phone`).
   - **B**: `adb shell settings put global mobile_data_always_on 1` —
     одноразово, переживает перезагрузку.
   - **C**: `adb shell pm grant <package> android.permission.WRITE_SECURE_SETTINGS` —
     даёт приложению право, после чего можно перетыкать галку и
     получить кнопку `Enable`.
   - Проверить, что прижилось: `adb shell settings get global mobile_data_always_on` →
     должно быть `1`.

**Жёсткий запрет на устройствах без поддержки split.** Если устройство
не умеет держать оба интерфейса одновременно — приложение **не даст
включить галку** до тех пор, пока проблема не будет устранена:

- Если на этом устройстве уже был запущен self-test и он показал
  одинаковые IP (`SAME_IP`) в течение последних 24 часов → при клике
  на галку появится диалог `Wi-Fi return: already verified not
  working` с инструкциями и галка автоматически снимется. Это
  «короткая память» — после 24 часов или после успешного `Enable`
  через preflight приложение даст попробовать снова.
- При preflight `BLOCKED`:
  - кнопка `Enable` (если есть `WRITE_SECURE_SETTINGS`) → успешный
    `mobile_data_always_on=1` → галка остаётся отмеченной;
  - `Enable` не сработал (ROM зарезал запись) → автоматически
    снимется + Toast «Wi-Fi return disabled: ROM rejected the system
    write»;
  - `Show instructions` → автоматически снимется + Toast «manual fix
    required»;
  - `Ignore` → автоматически снимется + Toast «device blocks parallel
    transports».

То есть единственный способ оставить галку включённой на «плохом»
устройстве — это успешно починить `mobile_data_always_on` (через
auto-fix или вручную). Это сделано чтобы агент **никогда не
запускался в заведомо нерабочем состоянии** с Wi-Fi return.

## 4. Ротация IP

> ⚠️ **Для любой ротации IP обязателен root.** Без root ни ручная
> ротация (`↻`), ни авто-ротация по `REBOOT` от сервера **не работают** —
> кнопка отрабатывает «вхолостую», IP остаётся прежним. Это касается
> и базового 2-шагового цикла, и всех fallback-методов (APN swap, IMEI
> rotation). Если на устройстве нет Magisk/SuperSU — рассчитывать на
> ротацию не нужно; либо рутуйте устройство, либо выключайте серверный
> REBOOT для этого агента.

### 4.1. Когда срабатывает
- **Автоматически** — когда сервер шлёт `REBOOT` через регистратор.
  В логах: `REBOOT received from registrator`. Сервис **не убивает себя**,
  только цикл сети; статус-бейдж переключается в `ROTATING · <stage>`.
- **Вручную** — кнопка `↻` на главном экране. Останавливает агента,
  делает цикл, запускает обратно. На Wi-Fi кнопка выдаёт ошибку — отключите
  Wi-Fi, чтобы ротация била по сотовому.

### 4.2. Что происходит внутри
Базовый алгоритм (без fallback) занимает ~10–75 секунд **и требует root**:

1. **Проба root** (`su -c true`). Если root недоступен — ротация
   прерывается, дальнейшие шаги не выполняются.
2. **Шаг 1 (10 с)**: сохранить текущий RAT, форсировать GSM-only, включить
   airplane mode, перезапустить ril (`setprop ctl.restart ril-daemon`),
   подождать 10 с, выключить airplane, восстановить RAT, проверить IP.
3. **Шаг 2 (60 с)**: то же самое, но с увеличенной паузой — даёт оператору
   время полностью освободить PDP-контекст.
4. (Опционально) **APN swap** — если включён и шаги 1–2 не помогли.
5. (Опционально) **IMEI rotation** — если включён и предыдущие шаги не
   помогли.

Все шаги пишут в `agent.log` и в `LOGS`-панель — что именно выполняется,
видно в реальном времени.

Если новый IP получен — он сохраняется в `nat_ip`, событие пишется в
`analytics/cycle_events.jsonl`, и агент стартует обратно. Toast
показывает результат: «IP changed in N try(s) / Xs: A.B.C.D → E.F.G.H».

### 4.3. Авто-стоп подавлен во время ротации
Watchdog «нет интернета 30 с → стоп» **отключён**, пока активна
авто-ротация — иначе он бы остановил агента ровно в тот момент,
когда сотовое опускается на 60 секунд по второму шагу. Стоп по батарее
**не** подавляется — низкий заряд останавливает в любом случае.

### 4.4. Если ротация не работает

#### A. Toast «Auto-cycle unavailable» / `no_toggle_method` в логе
На устройстве **нет root**. Ротация без рута физически не может ни
дёрнуть RIL, ни сделать airplane-cycle на нужных Android-версиях.
Решение: установить Magisk (или другой root-менеджер), дать
приложению разрешение на `su`, повторить ротацию.

Проверить руками: выполните в adb-shell или терминале на устройстве
```
su -c id
```
Если выводит `uid=0(root) …` — root работает. Если `su: not found`
или окно SuperUser-приложения отказывает — нужно сначала починить
root, потом возвращаться к ротации.

#### B. Цикл прошёл, но IP не сменился (`ip_unchanged`)
Базовый цикл с двумя шагами оператор «не отпустил». По возрастанию
агрессивности:
1. Включить `APN swap` в настройках (нужно root). Работает, если на
   SIM ≥ 2 разных APN.
2. Включить `IMEI rotation`, выбрать метод. Эффективность зависит
   от чипсета и установленного Magisk-модуля.
3. Подождать — некоторые операторы держат PDP-контекст 5–10 минут,
   повторите ротацию через 5 минут.

#### C. Не помогает ничего, включая `adb reboot`
Это IMSI-биндинг (привязка IP к SIM-карте на стороне оператора —
например, наблюдалось у Lifecell UA). **Программного решения нет**:
ни airplane-cycle, ни RAT switch, ни APN swap, ни IMEI-spoof, ни
полный ребут устройства IP не сменят. Помогает только физическая
смена SIM или замена SIM-карты у оператора.

**Диагностический тест**: сделайте `adb reboot`. Если IP после
полной перезагрузки не сменился — это IMSI-биндинг, не баг
приложения.

#### D. APN swap пишет в логе «no alternate APN found»
На SIM прописан только один APN под текущим `numeric`. Можно либо
вручную добавить второй (например, `*.mms`-вариант оператора) через
системные настройки `Settings → Mobile network → APN`, либо
отключить `APN swap`.

#### E. IMEI rotation падает с «su not found» / «command not found»
> ⚠️ Напоминаем: **функция IMEI rotation не протестирована командой**
> (см. §3.8). Используйте на свой риск.

Причины ошибки:
- **Нет root.** Приложение само IMEI не меняет — оно вызывает внешнюю
  команду через `su -c`. Без root вызов сразу падает.
- **Нет нужного Magisk-модуля**, который должен делать саму смену:
  - для метода `props` — модуль `MagiskHidePropsConfig` (и это всё
    равно только Android-уровень, см. §3.8);
  - для метода `magisk-imei` — модуль `magisk-imei` (бинарь должен
    оказаться в `PATH` у `su`);
  - для метода `custom` — то, что вы сами поставили и прописали в поле
    `Custom root command`.

Что сделать:
1. Проверить, что root есть: `su -c id` → `uid=0`.
2. Проверить, что команда вообще выполняется: `su -c '<ваша команда>'`
   из adb-шелла или терминала на устройстве. Если падает там же —
   проблема в модуле, не в приложении.
3. Если модуля нет / поставить не получается — отключите галку
   `IMEI rotation` и используйте только базовый цикл + APN swap.

### 4.5. Стадии ротации на бейдже
`ROTATING · <stage>` — `stage` приходит из лога ротации. Примеры:
- `attempt 1: airplane on + restart ril + RAT→GSM, sleeping 10s`
- `attempt 2: …`
- `attempt 3 (APN swap): preferapn 724 → 725 (life:) MMS/mms)`
- `verifying new IP via api.ipify.org`

Если стадия не двигается дольше 30 секунд — велик шанс, что радио
не возвращается; перезагрузите устройство.

## 5. Экран аналитики (`◫`)

Три раздела с фильтром периода `Day / Week / Month`:

### 5.1. Total traffic
- Суммарный объём за период;
- `↓ IN` / `↑ OUT` — поделено по направлениям;
- Число подключений за период.

### 5.2. Графики
- `TRAFFIC` — линия трафика во времени;
- `CONNECTIONS` — гистограмма подключений;
- `ROTATIONS` — stacked-bars (■ manual + ■ auto).

### 5.3. IP rotations
- Общее число ротаций за период;
- Раздельно `MANUAL` и `AUTO`;
- Частота (на день/час);
- Время последней ротации.

### 5.4. Recent rotations
Список последних попыток: время, было → стало, успешно/нет, причина
(`ok` / `ip_unchanged` / `no_toggle_method` / …), число попыток,
длительность.

### 5.5. Filter
По умолчанию — без фильтра. Можно отфильтровать данные по типу события
(см. dropdown `FILTER`).

### 5.6. Экспорт (`SAVE` в шапке аналитики)
Кладёт CSV в Downloads через системный chooser. В файле — все ротации
за период с теми же полями, что и в Recent rotations, плюг агрегаты
по бакетам.

### 5.7. Retention
Внизу экрана надпись `analytics retention: N days`. Изменяется в
основных настройках `⚙ → Analytics retention`.

## 6. Уведомления в шторке

В шторке могут быть три разных уведомления от приложения:

| Что видно | Когда появляется | Что значит |
| --- | --- | --- |
| **«Proxy Agent» (sticky, не свайпается)** | Пока работает сервис | Подключение активно. Текст обновляется каждую секунду: статус (`STARTING…/CONNECTING…/CONNECTED · ↓X ↑Y`), кнопка `Stop`. Удаляется при `STOP`, авто-стопе и при апдейте приложения (см. §7.6). |
| **«Proxy Agent stopped»** (одноразовое) | Срабатывание авто-стопа (батарея / нет интернета) | Содержит причину остановки. Тап открывает приложение. Свайпом убирается. |
| **«Proxy Agent — auto-restart blocked»** (одноразовое) | После апдейта, если автозапуск сервиса заблокирован OEM-защитником (см. §7.7) | Тап открывает приложение, чтобы можно было нажать `START` руками. Если такое появилось — нужно один раз пройтись по §7.7 чтобы в будущем не появлялось. |

Все три уведомления идут через один канал `proxy` (importance LOW —
не звенит, не вибрирует). Канал создаётся автоматически при первом
старте сервиса; если выключить его в системных настройках, sticky-
уведомление подключения тоже исчезнет — но сервис при этом
продолжит работать (Android требует FGS быть foreground'ом, но не
обязан показывать пользователю канал).

## 7. Быстрые рецепты

### 7.1. Первый запуск — через QR (основной путь)
1. Получите QR-код для агента (от менеджера, из чата, в виде картинки
   или текстом).
2. Открыть приложение → `⚙` → `SCAN QR`.
3. Выбрать источник в системном chooser:
   - **Live camera** — навести камеру на QR;
   - **Image from gallery** — выбрать скриншот QR;
   - **Paste from clipboard** — если QR пришёл текстом (скопируйте
     текст заранее).
4. Дождаться Toast «QR applied: host, port, key, …» — поля заполнятся
   автоматически, режим встанет в `Modem`.
5. `Save` в диалоге настроек → нажать `START` → дождаться зелёного
   `CONNECTED`.
6. Если бейдж висит в `CONNECTING…` дольше 30 с — раскройте `LOGS`,
   ищите `uplink AUTH denied` (ключ неверный) или
   `uplink: transport dial failed` (сеть/firewall).

> Если QR на руки не выдали — есть резервный путь через `⚙` → `IMPORT`
> (текстовый файл с `key=value`-строками) или ручной ввод полей
> (`Host` / `Port` / `Agent Key` обязательны).

### 7.2. Подключение долго не поднимается
1. Проверить, что в шапке указан корректный публичный IP — если
   `—` или пусто, проблема со стороны устройства.
2. Раскрыть `LOGS`, поискать последнюю строку с `uplink`.
3. `↻` — иногда оператор после смены сети не подцепляется до явной
   ротации.

### 7.3. Сбор лога для разработчика
1. `LOGS → SAVE` → отправить в чат/почту.
2. По возможности приложить:
   - версию приложения (показана под шапкой),
   - модель устройства и Android-версию (есть в заголовке экспорта
     лога),
   - что делали перед проблемой.

### 7.4. Включить полноценную автономную работу
1. `ALLOW BACKGROUND (BATTERY WHITELIST)` — добавить приложение в
   whitelist Android.
2. `Auto-stop below battery` → выставить порог (обычно 10–15%),
   чтобы устройство не разрядилось в ноль.
3. Установить **root** (Magisk) — без него ротация IP работать не
   будет ни вручную, ни автоматически по серверному `REBOOT`.
4. **На Xiaomi/Huawei/Samsung/OnePlus/Oppo/Vivo** дополнительно
   пройти по §7.7 и разрешить автозапуск — иначе сервис не
   поднимется автоматически после обновления приложения, и кто-то
   должен будет открывать приложение и жать `START` после каждого
   апдейта Play Store.

### 7.5. Сменить регистратор «на горячую»
1. `⚙` → отредактировать `Host` / `Port` / `Key` / `ID` → `Save`.
2. Toast `Saved — restart agent to apply` — нажать `STOP`, потом
   `START`. Изменения движка/режима требуют именно stop+start
   (Toast `Saved — stop & restart to apply`).

### 7.6. Что происходит при обновлении приложения

При установке нового APK поверх работающего Android **жёстко
убивает оба процесса** (`:main` и `:proxy`) — это поведение системы,
не приложения. Активная сессия с регистратором и все туннели в
момент апдейта обрываются. Это неизбежно.

После апдейта приложение пытается **автоматически восстановить
сессию**, если до этого она была активна (не был нажат `STOP` и не
сработал авто-стоп):

1. Android доставляет в новое приложение broadcast
   `MY_PACKAGE_REPLACED`.
2. Внутренний receiver (`PackageReplacedReceiver`) проверяет файл
   `was_running` — он сохраняется при каждом старте сервиса и
   удаляется при остановке. Если файл есть — значит сессия была
   живая, апдейт прервал её.
3. Receiver читает `Host`/`Port`/`Key`/`ID` из настроек и сам
   запускает `ProxyService`.
4. Через 2-5 секунд агент дозванивается до регистратора, статус
   становится `CONNECTED`, **аптайм начинает с нуля** (это новая
   сессия, не продолжение старой).
5. Клиенты на ваших таргетах переподключатся сами по обычной
   логике переподключения после сетевого обрыва.

**Что видит админ:**
- Сразу после апдейта при открытии приложения — `DISCONNECTED`,
  затем через несколько секунд → `STARTING…` → `CONNECTING…` →
  `CONNECTED`.
- В `LOGS → SAVE` экспорте логов в начале новой сессии увидите
  маркер вида `=== app v1.0.347 (build 347) pid=12345 ===` — это
  отметка от нового процесса.
- В `logcat` (через adb) — строки с тегом `ProxyAgent.PkgReplaced`:
  `MY_PACKAGE_REPLACED received`, далее
  `auto-restarted ProxyService (engine=… mode=…)`.

**Когда автозапуск НЕ сработает** — самая частая причина:
**встроенные «защитники» OEM-прошивок блокируют broadcast'ы**. На
Pixel / AOSP / большинстве европейских телефонов всё работает «из
коробки», но Xiaomi/Huawei/Samsung/OnePlus/Oppo/Vivo по умолчанию
ограничивают автозапуск приложений из background. См. §7.7.

Если автозапуск не сработал — в шторке появится отдельное
уведомление **«Proxy Agent — auto-restart blocked»** с пояснением
причины и тапом в приложение. Это не sticky-уведомление — оно
исчезнет после тапа или свайпа. Пользователь открывает приложение
и нажимает `START`. UI после апдейта честно показывает
`DISCONNECTED` (а не фейковый `CONNECTED` со старым аптаймом, как
было до фикса).

> **Окно отсутствия уведомления** между смертью процесса и
> рестартом ≈ 1–3 секунды. Это поведение Android (foreground-
> service notification удаляется ОС вместе с убитым процессом).
> Если автозапуск **успешен** — sticky-уведомление о подключении
> вернётся в шторку само через эти 1–3 секунды (текст эволюционирует
> `STARTING…` → `CONNECTING…` → `CONNECTED · ↓X ↑Y`). Если за 5–10 с
> ни sticky-уведомления, ни уведомления «auto-restart blocked» не
> появилось — значит broadcast вообще не дошёл, нужны действия из
> §7.7.

### 7.7. Разрешить автозапуск после обновления (по вендорам)

Все приведённые ниже разрешения нужны **один раз** при установке
приложения. После этого `MY_PACKAGE_REPLACED` доходит до receiver и
сервис стартует сам.

> **Как проверить, работает ли autostart**: вручную нажмите `STOP`,
> переустановите APK поверх (`adb install -r app-release.apk` или
> через Play Store). Если после установки сервис **не** стартовал
> сам — autostart заблокирован, нужны действия ниже. Если стартовал
> — всё ок (мы не хотим автозапуск после ручного STOP, но после
> апдейта работающей сессии — хотим).

#### Xiaomi / Redmi / POCO (MIUI 12+)

1. **Настройки → Приложения → Управление приложениями → Proxy
   Agent → Автозапуск** — включить.
2. **Настройки → Приложения → Управление приложениями → Proxy
   Agent → Контроль активности** (на старых MIUI — «Battery
   saver») → выбрать **«Без ограничений»**.
3. **Настройки → Аккумулятор → Энергосбережение → Proxy Agent →
   Без ограничений**.

Дополнительно если телефон агрессивно убивает фоновые процессы:
- На экране недавних задач (multi-task) сделать «pin» (значок
   замка) на иконке приложения — это блокирует свайп-кил.
- Отключить **«Контроль памяти»** для приложения в Security app.

#### Huawei / Honor (EMUI 10+, HarmonyOS)

1. **Настройки → Приложения → Запуск приложений → Proxy Agent** →
   переключить из «Авто» в **«Управление вручную»** → включить
   **все три тумблера**: «Автозапуск», «Косвенный запуск», «Запуск
   в фоне».
2. **Настройки → Батарея → Расход батареи → Proxy Agent →
   Запускать в фоновом режиме** — включить.
3. **Настройки → Батарея → Расход батареи → ⋮ →
   Производительность → разрешить запуск дополнений в фоне**.

EMUI особенно агрессивно блокирует broadcast'ы — на нём
обязательно нужны все три тумблера в «Запуск приложений», иначе
`MY_PACKAGE_REPLACED` не дойдёт.

#### Samsung (OneUI 3+)

1. **Настройки → Приложения → Proxy Agent → Батарея → Разрешить
   фоновую активность** — включить.
2. **Настройки → Обслуживание устройства → Батарея → Ограничения
   фоновой работы → Спящие приложения** — убедиться что Proxy
   Agent **не в списке**. Если в списке — удалить.
3. **Настройки → Обслуживание устройства → Батарея → Ограничения
   фоновой работы → «Никогда не переводить в режим сна»** —
   добавить Proxy Agent.

OneUI 5+ дополнительно: **Настройки → Батарея → Дополнительно →
Оптимизация использования батареи** → найти Proxy Agent →
**«Без ограничений»**.

#### OnePlus / Oppo / Realme (ColorOS, OxygenOS 12+)

1. **Настройки → Приложения → Управление приложениями → Proxy
   Agent → Расход батареи** → выбрать **«Разрешить активность в
   фоне»** или **«Без ограничений»**.
2. **Настройки → Конфиденциальность → Запуск приложений → Proxy
   Agent** → включить **«Разрешить автозапуск»** + **«Разрешить
   запуск из других приложений»** + **«Разрешить запуск в фоне»**.

На некоторых ColorOS-сборках раздел называется **«Управление
автозапуском»** и лежит в **Настройки → Аккумулятор**.

#### Vivo / iQOO (Funtouch OS, OriginOS)

1. **Настройки → Аккумулятор → Использование батареи → Proxy
   Agent → Расход энергии в фоне** → выбрать **«Разрешить»**.
2. **iManager / Настройки → Управление приложениями → Автозапуск
   приложений → Proxy Agent** — включить.
3. **iManager → Защита приложения → Proxy Agent** — добавить в
   защищённые.

#### Стоковый Android / Pixel / Nothing / Motorola

Обычно работает без настроек. Достаточно один раз нажать
`ALLOW BACKGROUND (BATTERY WHITELIST)` в самом приложении (это
запросит у системы освобождение от Doze) — этого хватает на 95 %
устройств. Если автозапуск всё равно не работает на Android 14+:

1. **Настройки → Приложения → Proxy Agent → Батарея →
   Не ограничено**.
2. Перезагрузить устройство (некоторые Android-сборки кэшируют
   ограничения broadcast-приёма до перезагрузки).

#### Общий fallback

Если ни один из методов не сработал на конкретном устройстве,
**автозапуск после апдейта неработоспособен на этом телефоне**
средствами приложения. Варианты:

1. **Ручной старт** после каждого апдейта (пользователь открывает
   приложение, нажимает `START`).
2. **Отключить автообновление** Play Store для этого приложения
   (Play Store → значок профиля → Управление приложениями →
   Управление → Proxy Agent → ⋮ → снять галку «Автообновление»).
   Тогда апдейты только когда админ сам это инициирует, в удобный
   момент.
3. **Установка через `adb install -r`** в окне обслуживания —
   админ сразу после установки нажимает `START`.

## 8. Куда смотреть когда совсем непонятно

| Симптом | Что проверить |
| --- | --- |
| Бейдж `NOT CONFIGURED` | Не заполнены Host/Port/Key — `⚙` или импорт QR |
| Бейдж `ERROR` | `LOGS` — последние строки с `error`/`failed` |
| `AUTO-STOPPED · Battery N% ≤ T%` | Заряд упал ниже порога. Зарядить или поднять порог |
| `AUTO-STOPPED · No internet (Xs)` | Сеть пропадала ≥ 30 с. Проверить сотовое/Wi-Fi |
| `CONNECTING…` висит | Логи → `uplink AUTH denied` = ключ; `dial failed` = сеть |
| `↻` не реагирует | Wi-Fi включён (выключить) или идёт авто-ротация (подождать) |
| После обновления приложения статус `DISCONNECTED`, хотя раньше был `CONNECTED` | Это нормально: ОС убила сервис при апдейте (см. §7.6). Подождите 2-5 секунд — автозапуск должен поднять сессию. Если через 15 с всё ещё `DISCONNECTED` — ваш OEM блокирует автозапуск, см. §7.7. Просто нажмите `START` руками. |
| Аптайм сильно больше реального времени работы | **Только если приложение НЕ обновлялось** — это значит сервис продолжает работать корректно с момента старта. Если в шапке (`v…`) — новая версия, а в логах внизу старые временные метки, и аптайм при этом большой — приложите лог в чат разработчику, это баг (фикс уже в 1.0.347+, не должен повторяться). |
| После апдейта телефон в режиме самолёта / без сотовой | Ротация IP была прервана апдейтом посреди airplane-on. При следующем запуске приложение само должно выключить airplane mode (см. §4.2, *interrupted-cycle recovery*). Если не выключилось через 10 с — приложение не имеет root или WRITE_SECURE_SETTINGS; выключите airplane mode вручную. |
| После апдейта телефон в 2G/3G, хотя обычно LTE | То же самое — ротация была прервана между «GSM-only switch» и «restore RAT». При запуске приложение пытается вернуть RAT в исходный (нужен root). Если не помогает — **Настройки → Сеть → Предпочитаемый тип сети → LTE** (или какое было). |
| `↻` отрабатывает «вхолостую», IP прежний | Скорее всего нет root — проверьте `su -c id`. Без root ротация не работает (§4) |
| Toast «Auto-cycle unavailable» / `no_toggle_method` | Нет root. Установить Magisk и дать приложению `su` |
| Ротация не меняет IP даже с root | См. §4.4 — попробовать `adb reboot` для диагностики IMSI-биндинга |
| Сервис умирает в фоне | Battery whitelist (§1.6) + `Auto-stop` = `Off` |
| Аналитика пустая | Никаких подключений ещё не было, либо retention `Day` и сегодня запусков не было |
| Галка `Return traffic … over Wi-Fi` задизейблена | Стоит режим `Residential (via balancer)` — на нём фича не работает (§3.9). Переключитесь в `Modem`, если возможно. |
| Включил Wi-Fi return, экономии нет | В виджете строка `↺ uplink via cellular …` (жёлтая)? Wi-Fi не держится — см. §3.9 про `mobile_data_always_on`. Если строки нет вообще — релей не поднялся, в `LOGS` ищите `wifi_return:`. |
| Диалог `Cellular may drop while on Wi-Fi` при включении галки | Устройство отрубает сотовую при Wi-Fi. Следуйте инструкциям из диалога (см. §3.9) или нажмите `Ignore`, если экономия не критична. |
| Хочу проверить, реально ли аплинк идёт по Wi-Fi | Виджет показывает два IP. Голубой блок с разными IP (cellular и Wi-Fi) — split routing подтверждён ВДВОЙНЕ: self-test делает три probe (Wi-Fi/cellular/default) и проверяет что default==cellular, то есть SDK target dials действительно уходят через сотовую. Жёлтый `↺ uplink via cellular …` — релей включён, но Wi-Fi нет. Красный `✗ … DISABLED · split routing not confirmed` — устройство не разделило трафик ИЛИ default route не cellular, релей отключился (см. §3.9). |
| Друг говорит target видит Wi-Fi IP вместо мобильного | Класс. (1) Уверены что используется NATIVE engine? Wi-Fi return требует NATIVE. При ставке галки приложение должно было переключить движок. (2) В шапке log-экспорта `[WI-FI RETURN]` → `Split-Routing:` должен быть `VERIFIED`. Если `LEAK_DETECTED` — релей выключен авто, агент работает напрямую через cellular (так что Wi-Fi утечки уже нет). (3) Если виджет показывает голубой блок, но в `wifi_info.json` `test_result=LEAK_DETECTED` — это бага, пришлите лог. |
| В логе строка `requestNetwork(Wi-Fi) failed: was not granted CHANGE_NETWORK_STATE` или Split-Routing `INCONCLUSIVE (both probes failed)` | **Версия приложения ниже 1.0.56.** Был баг: в манифесте отсутствовал `CHANGE_NETWORK_STATE`, из-за чего весь Wi-Fi return фактически работал в leak-режиме (target видел Wi-Fi IP). Обновите до 1.0.56+, там манифест исправлен. После обновления self-test пройдёт штатно. |
| После обновления Wi-Fi return сразу красный warning, релей выключился | Initial self-test не смог завершиться (`BOTH_FAILED`). Обычно это значит что система не разрешает параллельные `requestNetwork` — экзотический ROM, или что-то блокирует. Релей отключается по политике "fail loud" — лучше работать напрямую через cellular чем тихо leak'ать. Снимите галку, либо разбирайтесь с системными настройками. |
| Галка `Return traffic … over Wi-Fi` сама снимается при клике | Сработал hard gate (§3.9). Прочитайте Toast — он скажет причину: `ROM rejected the system write`, `manual fix required`, или `device blocks parallel transports`. Следуйте инструкциям и попробуйте снова. |
| Диалог `Wi-Fi return: already verified not working` при ставке галки | Предыдущий self-test за последние 24ч показал SAME_IP. Исправьте `mobile_data_always_on=1` (см. §3.9), подождите 24ч **или** удалите файл `wifi_info.json` в `filesDir` через adb, и попробуйте снова. |
| На виджете в `Connected to registrator` пишет `127.0.0.1:<port>` вместо реального хоста | Старая сборка без `applyCurrentRegistrator`. Обновите приложение до версии с Wi-Fi return v3+ — там SDK логирует loopback (это правильно для сетевого стека), но виджет автоматически подменяет на реальный регистратор. |
| Красный warning `split routing not confirmed` появился — что делать | Устройство не умеет держать оба интерфейса разделённо. Включите `mobile_data_always_on=1` (диалог при ставке галки уже предлагает это, см. §3.9). Перезапустите сервис — self-test пройдёт заново. |
| `AUTO-STOPPED · Wi-Fi return: split routing not confirmed` | Self-test обнаружил `SAME_IP` или `LEAK_DETECTED` — релей откатился, агент остановлен. Уберите галку `Return traffic … over Wi-Fi` или включите `mobile_data_always_on` (см. §3.9), запустите снова. |
